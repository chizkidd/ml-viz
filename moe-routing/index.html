Mixture of Experts: Routing, Collapse & Serving

Sparse MoE replaces one monolithic FFN with N specialist experts and a router that activates only top-k per token. Decoupling total parameters from per-token FLOPs unlocks huge capacity—but creates three engineering problems: expert buffer overflow, router collapse during training, and batch-dependent serving memory bandwidth. Tabs 1–2 are computed live from seeded browser simulations; Tab 3 combines published specs + formula.

Token-to-expert routing & capacity buffers

computed live
Each of the 32 tokens in a batch computes softmax router probabilities pi(x) = softmax(h(x) / T) and routes to its top-k experts. Fixed-buffer MoE caps each expert at capacity = ceil(C · Ttok · k / N) slots: excess tokens overflow and are dropped (falling back to the residual stream), while unused slots become wasted padding. Router collapse vs Switch aux loss vs DeepSeek-V3 bias

Early experts that receive more tokens get more gradient updates, become better, and earn even higher router scores—starving the rest into dead experts. The MoE serving paradox: active FLOPs vs total VRAM & batch bandwidth

published specs + formula
At batch size B = 1, an MoE model reads only its active parameters from HBM—giving dense-small speed with dense-large capacity. But as batch size B grows, independent tokens activate different experts: by coupon-collector expectation, a decode step hits E[experts] = N(1 − (1 − k/N)B) distinct experts, driving weight reads toward all total parameters while VRAM must always hold all N experts in memory.
